# Test Harness — テスト設計駆動の開発スキル

mizchi氏の「テスト設計こそがプロダクト設計」の原則に基づき、テストハーネスの構築と継続的な強化を支援する。

## 原則

8つの原則が全フェーズの判断基準になる。各フェーズの作業中に判断に迷ったら参照すること。

📋 [テスト設計駆動の8原則](./references/principles.md)

---

## フェーズ判定

作業を始める前に、プロジェクトの現状を確認して適切なフェーズを選択する。

### 判定フロー

```
テストランナーが導入されているか？
  ├─ No → Phase 1: init
  └─ Yes → テストケースが存在するか？
              ├─ No → Phase 1: init
              └─ Yes → 何をしたいか？
                        ├─ テストケースの追加・変更 → Phase 2: strengthen
                        ├─ テストインフラの整備 → Phase 3: infra
                        └─ 不明 → Phase 2: strengthen（デフォルト）
```

### 各フェーズの概要

| フェーズ | 目的 | いつ使うか |
|---------|------|-----------|
| [init](./references/init.md) | ハーネスの初期構築 | テスト基盤がゼロの状態から足場を作る |
| [strengthen](./references/strengthen.md) | テスト設計・追加・強化 | 新機能追加、バグ修正、テストカバレッジ改善 |
| [infra](./references/infra.md) | テストインフラ整備 | CI連携、レポート、再現性・診断性の改善 |

---

## Hook: コード変更時のテスト強化

コード変更を伴う作業（機能追加、バグ修正、リファクタリング）において、以下の条件のいずれかを満たすとき、作業完了前にstrengthenフェーズの実行を検討する。

### 発火条件

1. **新しい関数・モジュールの追加**: 新たにexportされた関数、または新しいファイルが作成された
2. **既存テストの失敗**: コード変更により既存テストがfailした
3. **Strict Gate対象の変更**: 原則3の4軸でStrict寄りと判定される機能に変更が入った
4. **バグ修正**: バグを修正する場合、修正前にそのバグを再現するテストを書く

### 発火しない条件

- ドキュメントのみの変更
- 設定ファイル（.env, tsconfig等）のみの変更
- テストコード自体の変更（テストのテストは書かない）
- 依存パッケージのアップデートのみ（ただしテスト実行は行う）

### 実行方法

発火条件を満たした場合:
1. まず既存テストを全実行し、現状を把握する
2. [strengthen](./references/strengthen.md) の手順に従い、変更箇所に対するテストを追加する
3. Strict Gateテストが全pass、Soft Gateテストの合格率が低下していないことを確認する

---

## 運用原則

- テストは「最初の1つ」から始めて漸進的に育てる。完璧なテストスイートを一度に作ろうとしない
- Strict Gateは少なく保つ（全テストの20-30%が目安）。増やしすぎると開発が止まる
- テストが通らないコードをmergeしない。ただしSoft Gateのfailは許容する
- テスト自体の妥当性を疑う習慣を持つ（原則7）
