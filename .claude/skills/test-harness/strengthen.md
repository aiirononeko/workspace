# Phase 2: strengthen — テスト設計・追加・ハーネス強化

既存のテスト基盤に対して、テストケースの追加・品質ゲートの設計・テスト妥当性の監査を行うフェーズ。

---

## 前提条件

このフェーズは以下を満たすときに実行する:
- テストランナーが導入済み
- 最低1つのテストケースが存在する

満たさない場合は [init](./init.md) を先に実行する。

---

## トリガー条件

以下のいずれかに該当するとき、このフェーズを実行する:
- 新しい関数・モジュールが追加された
- 既存の関数のシグネチャや振る舞いが変更された
- バグが発見された（バグ→テスト追加→修正の順序で対応）
- ユーザーが「テストを追加したい」「テストを強化したい」と明示した
- 既存テストがfailしている

---

## 手順

### Step 1: 現状の把握

既存のテストを実行し、現在の状態を把握する:
- 全テスト数、pass/fail数
- Strict Gate対象テストの合格率
- テストされていない関数・モジュールの一覧

### Step 2: テスト対象の選定

ユーザーとの対話で以下を明らかにする:

**新機能追加の場合:**
- 「追加した機能は何ですか？」
- 「その機能が壊れたとき、ユーザーにとってどの程度深刻ですか？」（原則3の4軸で判定）
- 「入力と期待する出力の具体例を教えてください」

**バグ修正の場合:**
- 「どのような入力でバグが発生しましたか？」
- 「期待する出力は何ですか？」
- そのバグを再現するテストを最初に書く（Red→Green）

**定期強化の場合:**
- テストカバレッジの低い箇所を特定
- 原則3の4軸でStrict/Soft判定し、Strict寄りのものから優先

### Step 3: テスト層の決定

原則2に従い、追加するテストがどの層に属するか決定する:

```
Layer 4: E2Eシナリオ
Layer 3: ツール連携・統合
Layer 2: 判断ロジック
Layer 1: データ変換・純粋関数
```

下位層のテストが不足している場合、上位層よりも下位層を優先する。上位層のテスト失敗の原因が下位層にある場合（逆流）、下位層にテストを追加してから上位層に戻る。

### Step 4: テストケースの設計

各テスト対象に対して、以下の観点でケースを設計する:

**純粋関数（Layer 1-2）の場合:**
- 正常系: 代表的な入力パターン
- 境界値: 空入力、最大長、型境界
- 異常検知: 「検知できなければプロダクトが壊れている」ケース
- 誤検知防止: 「正常を異常と判定しない」ケース

**非決定的関数（LLM呼び出し等）の場合（原則8）:**
- モデルバージョンをテストファイル内にコメントで記録する
- 可能ならseedを固定して決定的にする
- 出力の「構造」を検証する（JSONスキーマ、必須フィールドの存在等）
- 出力の「意味」を検証する場合は、禁止パターンの不在（否定条件）で検証する
  - 例: `expect(output).not.toMatch(/させてもら/)` のように「やってはいけないこと」を検証
- 統計的受け入れが必要な場合: N回実行のうちM回合格を閾値とする。閾値はテスト名やコメントに明記する

### Step 5: Strict/Soft Gateの設定

追加したテストケースごとに、Strict/Softを明示する。

方法はプロジェクトの規模に応じて選ぶ:
- **小規模**: テストファイル名やdescribeブロックで分離（例: `*.strict.test.ts` / `*.soft.test.ts`）
- **中規模**: テストランナーのタグ機能（例: vitestの `test.concurrent` やカスタムタグ）
- **大規模**: テストスイートごとにCI設定で分離

Strict Gateのテストが1つでもfailしたらマージをブロックする設定を推奨する（infra フェーズで実装）。

### Step 6: テスト妥当性の確認（原則7）

新規テストを追加するたびに、既存テストの妥当性も確認する:

- **false negative の確認**: 既知のバグがある入力を与えて、テストがちゃんとfailするか
- **false positive の確認**: テストの期待値が厳しすぎないか（許容すべき出力バリエーションをrejectしていないか）
- **テストの独立性**: テスト間に暗黙の実行順序依存がないか

---

## テスト追加のチェックリスト

テストケースを追加するたびに、以下を確認する:

- [ ] テスト対象の関数・モジュールを特定した
- [ ] テストの層（Layer 1-4）を決定した
- [ ] Strict/Soft Gateの分類を行った
- [ ] 正常系・境界系・異常検知系のバランスを確認した
- [ ] 非決定的要素がある場合、原則8の対策を入れた
- [ ] テストを実行し、期待通りにpass/failすることを確認した
- [ ] 既存テストが壊れていないことを確認した
