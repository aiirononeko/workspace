# Phase 3: infra — テストインフラ整備

テストの実行環境・レポート・CI連携など、ハーネスの4要件（再現性・可視性・追加容易性・診断性）を満たすインフラを構築するフェーズ。

---

## 前提条件

このフェーズは以下を満たすときに実行する:
- テストランナーが導入済み
- テストケースが複数存在する（目安: 5ケース以上）
- テストの実行・追加・診断のいずれかにおいて、手作業のコストが問題になり始めている

テストケースが5未満の段階では、このフェーズは時期尚早。[strengthen](./strengthen.md) でテストを増やすことを優先する。

---

## ハーネスの4要件と対応施策

### 1. 再現性

同じテストが、誰のマシンでも、いつ実行しても同じ結果になること。

**施策:**
- テストに必要な依存関係をlockfileで固定する（bun.lock / package-lock.json）
- LLMを使うテストでは、モデルバージョンを環境変数またはconfigで一元管理する
- seed固定が可能なAPIでは固定する
- テスト用のフィクスチャ（入力データ）をリポジトリに含める
- 環境依存（OS、ファイルパス等）をテストコード内で吸収する

### 2. 可視性

テスト結果が一目でわかること。

**施策（段階的に導入）:**

**最小構成（テスト数 < 20）:**
- テストランナーのデフォルト出力で十分
- pass/fail数のサマリが表示されればよい

**中規模（テスト数 20-100）:**
- Strict/Softの区分がテスト結果に表示される
- fail時にどの層（Layer 1-4）のテストかわかる
- テスト実行時間のサマリ

**大規模（テスト数 100+）:**
- JSONレポート出力（CI連携用）
- テスト結果のダッシュボード
- 合格率の推移グラフ

### 3. 追加容易性

新しいテストケースを追加するコストが低いこと。

**施策:**
- テストのボイラープレートを最小化する
  - テストヘルパー関数の整備（共通のsetup/teardown）
  - テストフィクスチャのテンプレート
- テストファイルの命名規則と配置規則を明文化する
  - 例: `src/foo.ts` のテストは `src/__tests__/foo.test.ts` or `tests/foo.test.ts`
- LLMテスト用のユーティリティを共通化する
  - API呼び出しのモック/スタブ
  - 統計的受け入れの共通ヘルパー（N回実行してM回合格を判定）

### 4. 診断性

テストがfailしたとき、原因がすぐわかること。

**施策:**
- assertionメッセージに「何を検証していて、何が期待と違ったか」を含める
  - NG: `expect(result).toBe(true)`
  - OK: `expect(result, "方向性反転が検知されるべき: '作ってもらう'が'作らせてもらう'に変化").toBe(true)`
- LLMテストでは、入力・出力・期待値をfail時にログ出力する
- 逆流分析の支援: 上位層テストのfailログから、下位層のどの関数を疑うべきかの手がかりを残す

## CI連携

テストケースが安定してきた段階で、CI（GitHub Actions等）に連携する。

### Strict/Soft Gateの分離実行

```yaml
# 例: GitHub Actions
jobs:
  strict-tests:
    # Strict Gateはマージブロック
    runs-on: ubuntu-latest
    steps:
      - run: bun test --grep "strict"
    # failでPRをブロック

  soft-tests:
    # Soft Gateは情報提供のみ
    runs-on: ubuntu-latest
    steps:
      - run: bun test --grep "soft"
    # failでもPRはブロックしない（continue-on-error: true）
```

### LLMテストの扱い

LLMを呼ぶテストはCIでの実行コストが高い。以下の戦略を検討する:

- **daily cron**: LLMテストは毎PR実行ではなく、日次で実行する
- **手動トリガー**: PRにラベル（例: `run-llm-tests`）を付けたときだけ実行する
- **コスト上限**: テスト実行あたりのAPI呼び出し上限を設ける

## リプレイログ（原則8）

LLMテストの再現性を確保するために、I/Oログを保存する仕組み。

**最小構成:**
```
tests/
  __replays__/
    convert-style-casual-001.json   # { input, output, model, timestamp }
    convert-style-formal-001.json
```

テスト実行時にログを保存し、failした場合にそのログを使って再現・診断できるようにする。
ログはgitに含めるかどうかはプロジェクトの判断による（APIレスポンスが大きい場合は.gitignoreする）。

## 段階的導入の指針

インフラは一度に全部作らない。以下の順序で段階的に導入する:

1. **テストランナーの導入と基本実行**（initフェーズで完了済み）
2. **Strict/Softの分離** — テストファイル名またはdescribeブロックで分離
3. **診断メッセージの改善** — failしたテストの原因がわかるようにする
4. **CI連携（Strictのみ）** — Strict GateテストをPRブロック条件にする
5. **テストヘルパーの整備** — 追加容易性の改善
6. **CI連携（Soft + LLM）** — 情報提供用・日次実行の追加
7. **レポート・ダッシュボード** — 合格率の推移を可視化

各段階は、前段階の運用が安定してから次に進む。
